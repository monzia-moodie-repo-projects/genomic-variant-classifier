# Defects recorded 2026-07-24

Every item below was found by measurement against the live repository or the live
cohort artifacts on 2026-07-24, and every one is open unless marked otherwise.
Numbering is stable; do not renumber.

## A. Blockers on the Phase 1 repair

**A1 -- the Step 1a single-definition guard fails on any complete tree.**
`tests/unit/test_review_status_tier.py::test_the_tier_map_is_defined_exactly_once_in_the_repository`
fails with 7 definitions found. 25 of 26 tests pass. The guard was validated in a
working directory that did not contain the six pre-existing maps; obtaining the
reported baseline of 1 requires a tree in which only the new module is visible.
Step 1a therefore cannot be committed green as written.

**A2 -- that guard's first assertion clause is dead code.** It builds its expected
string from `definitions[0]`'s own line number, so it can only be true when the
list has exactly one element that is the new module -- in which case the
`or len(definitions) == 1` clause is already true. The first clause can never
independently pass the assertion.

**A3 -- the guard is name-scoped and blind to a fourth production map.** It
matches only `ast.Name` targets equal to `REVIEW_STATUS_TIER`.
`src/genomic_variant_classifier/monitoring/clinvar_tracker.py:160` defines
`REVIEW_TIER`, a six-key class attribute, imported live by
`training/continual_trainer.py:126`,
`agent_layer/agents/reclassification_sentinel_agent.py:86` and
`scripts/run_drift_monitor.py:421`. The true count of tier-map definitions is
**eight**, not seven. Detection must be content-based, not name-based.

**A4 -- `test_collection_count_is_what_the_ratchet_expects` is a tautology.**
`EXPECTED_COLLECTED` is defined as `len(A) + len(B) + 1 + 1 + 4 + 1 + 1` and
asserted equal to `len(A) + len(B) + 8`. It never asks pytest how many items were
collected. Its docstring claims it makes the ratchet number impossible to guess
wrong; it does not.

**A5 -- `tiers_for` has no tests.** It is exported in `__all__`, it is the batch
application programming interface the pipeline will call, and it carries the
module's headline behaviour -- collecting every unmatched value with its row count
before raising. Nothing exercises it.

**A6 -- `tiers_for` re-implements the lookup instead of delegating to `tier_of`.**
Two independent implementations of one decision, inside the module written to
eliminate exactly that.

**A7 -- `TIER_MISSING` and `TIER_UNMATCHED` are both 5**, so the documented
distinction between them is unenforceable by return value, and
`test_every_value_observed_in_the_cohort_resolves`'s missing-token assertion
cannot fail.

**A8 -- `'no classifications from unflagged records'` would raise.** 121 rows via
`ReviewStatus`, 133 via `metadata.review_status`. In neither the map nor
`MISSING_TOKENS`. Needs a tier assigned in the same commit as the raise.

## C. Cohort and code hygiene

**C1 -- the module's documented usage is rejected by the module's own guard.**
`real_data_prep.py:29`, in the module docstring's Usage block, directs the reader
to `data/processed/clinvar_grch38.parquet`. `_assert_clean_cohort` at lines
468-488 raises on the 21,091 rows that file retains, with a message instructing
the reader to use `clinvar_grch38_clean.parquet` instead. Anyone following the
documentation gets an immediate `ValueError` telling them the documentation is
wrong.

**C2 -- undocumented dtype narrowing.** The raw artifact stores string columns as
Arrow `large_string`; both clean artifacts store them as `string`. Ten columns are
narrowed by the clean step and nothing records it. Concatenating raw with clean
raises on schema mismatch. This project already resolved a ClinGen dtype drift on
2026-06-13.

**C3 -- four columns are wholly null by type.** `transcript_id`, `allele_freq`,
`protein_change` and `fasta_seq` carry Arrow type `null` in all three artifacts.
`protein_change` being null at artifact level is the HGVSp parser gap visible in
the data.

**C4 -- `fasta_seq` is a dead column**, superseded by `fasta_seq_ref` and
`fasta_seq_alt` in the sequence artifact and retained as a null column in all
three.

**C5 -- `clinvar_grch38_clean.parquet` is not what its name says.** It is the raw
artifact minus 21,091 rows, PLUS a `ReviewStatus` column produced by
`augment_reviewstatus.py`, PLUS the dtype narrowing of C2. Three transformations
under a filename naming one.

**C6 -- the raw cohort is a 2026-03-23 snapshot of ClinVar**, four months old, and
it is the artifact `real_data_prep.py:29` names.

**C7 -- `metadata.review_status` is typed `string` in the raw artifact** while
every sibling string column there is `large_string`.

**C8 -- 53 `ref_mismatch` rows** in the sequence branch: the ClinVar reference
allele disagrees with GRCh38. A data-integrity signal, not a window failure.

**C9 -- 723 rows have no usable sequence window** and no consumer states how they
are handled.

**C10 -- the `pathogenicity` column is stale.** Full record in
`docs/measurements/MEASUREMENT_2026-07-24_pathogenicity-column-staleness.md`.

## D. Defects in the probes written during this session, and their fixes

**D1 -- CLOSED. The label-column probe read one hardcoded artifact and could not
distinguish a blocker from a finding by exit code.** Replaced from the ground up
by `scripts/probe_label_column_terms.py`, which reads its contract by abstract
syntax tree parse, accepts repeatable `--cohort`, and discriminates four exit
codes. Validated by reproducing the three figures the superseded probe measured.

**D2 -- CLOSED. The schema census inflated every distinct count by one**, because
`pyarrow.compute.unique` counts null as a distinct value. Raw `ref` is 38,496 real
distinct values, not 38,497; raw `alt` is 20,667, not 20,668. Corrected
2026-07-24 to report the non-null distinct count.

**D3 -- CLOSED. The census raised an unhandled `pyarrow.lib.ArrowInvalid` on an
artifact missing a required column and exited 1**, the code reserved for a
measured finding. A contract problem reported as a finding is worse than no check,
because the operator acts on it. Guarded by a schema check costing no row read.

**D4 -- CLOSED. The forensics probe over-reported would-raise rows by 669,664**,
because it compared values against the tier map alone and ignored
`MISSING_TOKENS`. Corrected to a three-bucket classification with per-bucket
totals.

**D5 -- CLOSED. The forensics VERDICT label was stale after the D4 refactor**,
reading "not a tier-map key" beside the would-raise count. A correct number under
a wrong label is the same defect as a wrong number.

**D6 -- CLOSED. A `Where-Object` pipeline result indexed with `[0]` returned the
first CHARACTER of a single-line result**, reporting the suite-size ratchet as `2`
instead of `2893`. PowerShell hygiene item 16: index `[0]` only on a result forced
to an array with `@()`.


## E. Defects found after DEFECTS_2026-07-24.md was first written

**D8 -- evidence committed one generation older than its tool.** The forensics package
installer preserved evidence files byte-for-byte while patching the probes that produced
them, so both evidence files landed one generation stale. Rule adopted: when a probe is
corrected, its evidence is regenerated in the same commit or the divergence is stated.
Closed by the regeneration at `0f5a253` and the union/transition rebuild at `1dbef92`.

**D9 -- a self-test asserted the defect it should catch.** `probe_cohort_schema_census.py`'s
self-test asserted the pre-correction inflated distinct counts (expecting 3 where the
non-null distinct is 2), so it went red the moment the production path was fixed. It had
been failing on origin since `60bea84`. Rule adopted: a correction is not complete until
the tool's own self-test has been re-run against it. Closed at `1dbef92`.

**D10 -- a correct number under a wrong label.** The forensics verdict line read "rows whose
review status is not a tier-map key" beside the would-raise count after the three-bucket
refactor. Cosmetic; corrected on next touch.

**D11 -- a dangling document reference.** `review_status.py` cited
`DECISION_2026-07-24_review-tier-scale_R2.md`, which was untracked when Step 1a landed.
Resolved when that document is committed with this change.

**D12 -- a verification hash was stated for a file that did not yet exist.** A SHA-256 was
printed for a commit-message file before the file was created. Fabricating a verification
hash in a hash-verified workflow is corrosive. Rule adopted: a hash is stated only after it
is computed from a file on disk, never in advance, never as a placeholder.

**D13 -- state asserted from an unread or partially-read file.** Twice a message opened by
asserting an outcome ("the installer ran clean", "same file as last turn") that had not been
read in full -- once from an empty attachment, once from reading only a file's tail. Rule
adopted: read the entire file before asserting anything about its content; same name and
same byte size do not imply same content.

**D14 -- a documented distribution table attributed one map's output to another map's
column.** `DECISION_R2` section 1's "Production filter (substring)" column and section 2.3,
and `PHASE1_SPEC` section 3's row-level table, presented `clean_cohort` exact-map values and
a mis-attributed 157,229 count as production-map results. Found by simulating both real maps
against the committed cohort value counts rather than trusting the tables. Corrected in the
commit that carries this appendix. The affected DECISIONS are unchanged: the tier-4
recommendation rests on ClinVar precedence ordering, not the row count, and
`no assertion criteria provided` genuinely maps to production tier 4.

## 2. What revision 1 established, and which still stands

Nothing in this section is disputed. It is restated so revision 2 is readable alone.

**The defect.** `scripts/augment_reviewstatus.py:64` converts every join miss into an
empty string:

    df["ReviewStatus"] = key.map(vmap).fillna("")   # unmatched -> "" -> tier 5

`src/genomic_variant_classifier/data/real_data_prep.py` maps `""` to review tier 5 and
then drops every row above `min_review_tier`, which the launch scripts set to 3. A join
failure is therefore indistinguishable from a legitimate ClinVar quality judgement.

**The magnitude.** The join fails on **98.834 percent of deletions**: 187,258 of 189,468
deletion rows have a blank `ReviewStatus`, against 5.771 percent of single-nucleotide
variants, 0.483 percent of insertions and 0.519 percent of multi-nucleotide and other
variants. Insertions are almost unaffected, and that asymmetry is the mechanistic
signature.

**The consequence.** At `min_review_tier=3`, deletions retain **1.023 percent** (1,938
of 189,468) against **86.237 percent** (163,391) using the nested field. **161,453
reviewed deletions are wrongly excluded.** The surviving cohort is 0.0521 percent
deletions against 4.2123 percent.

**The retention is label-correlated.** Pathogenic variants retain 34.556 percent (132,446
of 383,277) against 95.236 percent for likely-benign. **67,929 pathogenic variants are
wrongly excluded.** Any AUPRC compared across the affected and unaffected cohorts is
comparing different positive rates -- 14.145 percent against 18.546 percent -- not
different models.

**The remedy is already present in the data.** `metadata.review_status`, nested in the
source parquet, agrees with the top-level `ReviewStatus` on **3,974,573 of 3,974,573**
rows where both are populated, with **zero disagreements**, and rescues 178,563
deletions.

**One caveat revision 1 raised and revision 2 endorses.** Validation coverage of the
nested field is thin exactly where it matters: only 2,210 deletions have both fields
populated, 1.166 percent, against 94.229 percent for single-nucleotide variants. The
agreement is perfect where it can be checked and largely unchecked for the class the
remedy is meant to rescue. That is not a reason to reject the remedy; it is a reason to
validate it on deletions specifically before regenerating anything.

Revision 1 section 6.1 states:

> Residual caveat, both branches converging: the absence of the log line could in
> principle mean the `logger.info` did not yet exist rather than that the filter did not
> run. The filter and the log live inside the same `if "ReviewStatus" in df.columns:`

**That reasoning is factually wrong.** Verified 2026-07-24:

| Question | Command | Result |
| --- | --- | --- |
| When did the string `Review tier filter` enter `real_data_prep.py`? | `git log -S'Review tier filter' -- src/.../real_data_prep.py` | **`ee6e136`, 2026-05-08** -- and that commit is the migration that *moved* the file, so it existed earlier under the pre-migration path |

**The filter block, and its log line, existed at Run 14.** So the caveat does not close
because the code was absent. It closes because the **column** was absent: the branch
`if "ReviewStatus" in df.columns:` never executed, so no filter ran and no line was
logged.

**Revision 1's conclusion is unchanged and is now more strongly supported than its own
argument made it.** Runs 9 through 14 did not apply the review-tier filter. But the
stated mechanism was wrong, and anything built on that stated mechanism would have been
built on a false premise.

**Independent corroboration from a tracked artifact.** `outputs/run14/run14_master.log`
is committed to the repository, and contains **no** `Review tier filter` line. So does
`outputs/run10b_final/run10b_master_final.log`. The regime-v0 half of revision 1's log
table is confirmed from artifacts anyone can check.

**A limit on what can be confirmed.** `.gitignore:51` ignores `*.log`, so
`run15_run.log`, `run16_master.log`, `run17_smoke.log` and the rest are **not in the
repository**. The regime-v1 half of revision 1's table is verifiable only on the machine
that holds those logs. Revision 2 does not dispute it; revision 2 records that it is

**Those are smoke logs.** Verified 2026-07-24:

  dated 06-06.
- **`docs/METRICS.md` has no Run 16 row either.** Run 16 executed; its metrics were

- **Every Run 17 mention in `docs/CHANGELOG.md` is preparatory:** "Run-17 prep",

about the log evidence and imprecise about what it implies.

**This matters for containment**, because a retrospective invalidation and a forward
launch blocker are different governance acts with different costs.

## 6. Corrected scope -- by artifact lineage, not by run number

Adopted 2026-07-24 on external review. A run is affected **if and only if one or more of
its upstream artifacts descends from the defective cohort**. Run numbers are a
consequence of artifact state, not the primary object, because feature matrices, parquet
exports, out-of-fold predictions, probability calibrators, conformal calibrators, SHAP
values, permutation analyses, gene rankings, benchmark tables and figures all outlive the
runs that made them.

**Lineage states**, defined in `docs/CONTAINMENT_2026-07-24.md`:
`VALID`, `PROVISIONAL`, `AFFECTED`, `SUPERSEDED`, `REGENERATED`.

| Object | State | Basis |
| --- | --- | --- |
| `clinvar_grch38_clean.parquet` after `augment_reviewstatus.py` | AFFECTED | the join defect |
| `clinvar_grch38_clean_seq.parquet` after the same | AFFECTED | the join defect |
| every training split derived from either | AFFECTED | inherited |
| Run 15 artifacts, including its METRICS.md rows | AFFECTED | descends from the above |
| Run 16 artifacts | AFFECTED | descends from the above; no METRICS.md row exists |
| Runs 9 through 14 | not affected **by this defect** | the filter never ran; separately not comparable to regime v1 because the cohort differs |
| Run 17 | BLOCKED, not affected | has not executed |

**Published metrics are NOT declared invalid.** Revision 2 deliberately does not use the
word. The cohort is known to be biased. It is **not yet known** whether AUROC, AUPRC,
calibration or gene ranking change materially, and that cannot be known until the
repaired cohort is regenerated and the comparison measured. "Known defective" and "known
materially changed" are different claims requiring different evidence.

The wording adopted for Run 15's METRICS.md rows is therefore:

> These metrics were generated from a cohort subsequently found to contain a
> label-correlated deletion-selection defect. They remain archived for provenance but
> must not be compared directly with metrics from a repaired cohort.

## The harness (agent_layer/harness/correctness_harness.py)

Five stages, each failure string prefixed `[stage N] ` for attribution:

1. **smoke** -- every active base estimator imports and fits on a tiny slice without
   raising. Estimators enumerated BEFORE fit (base_estimators is cleared during fit,
   Issue H).
2. **config** -- required estimator init attributes present (e.g. KAN `test_size`
   set before `.fit()`).
3. **sanity** -- `fasta_seq` is real, not the `"A"*101` dummy; predictions are not
   constant.
4. **determinism** -- same seed -> identical ensemble probabilities.
5. **zero-audit** -- no non-binary engineered feature is ~all-zero (silent-zero
   class). A column is binary-exempt ONLY if its unique set is exactly {0,1}.

Public API: `run_correctness_harness(raw_df, *, inject_estimators=None,
simulate_kan_missing_test_size=False, zero_rate_threshold=0.95) -> HarnessReport`
(`passed`, `failures`, `warnings`, `stages_run`).

## Silent-zero mechanism (root understanding)

`engineer_features` consumes all 28 connector inputs via `df.get(col, default)`
(docstring L5: "All missing columns are filled with safe defaults"). A missing
connector never errors -- it defaults, usually to 0. So on a fully-populated input the
only numeric non-binary columns that stay ~all-zero are those whose default is
zero/sub-threshold and which no input can currently populate. That set is the
connector-dead / silent-zero class from the 2026-04-30 audit.

## KNOWN_ZERO_DEFAULT (21 columns) + build_reference_slice()

Promoted both into the harness module as the single source of truth (shared by the
unit test and G1 Section 14):

- `build_reference_slice(n=200, seed=7) -> pd.DataFrame` -- a fully-populated synthetic
  variant frame; every `engineer_features` input is supplied correctly-typed and
  in-range so all derivable + connector features come alive.
- `KNOWN_ZERO_DEFAULT: frozenset[str]` -- the 21 empirically-derived dead-connector
  columns: af_1kg_{afr,amr,eas,eur,sas}, cadd_high, finngen_af_{fin,nfsee},

## Debugging the Section 14 invocation (4 iterations -- lesson recorded)

The static checks all passed (PS `ParseFile` OK; extract-the-here-string-to-a-file
probe ran the embedded Python green with correct `HARNESS_JSON`), yet the live gate
failed three times with `m = _re.search(rfeature ... '(' was never closed` -- the
regex string `r"feature '([^']+)'"` collapsed to `rfeature`.

- Iter 1 (expandable `@"..."@`): failed. Hypothesised PS here-string expansion.
- Iter 2 (literal `@'...'@`): STILL failed identically -- disproving the expansion
  theory (the on-disk bytes were confirmed correct via substring read).
- Root cause: passing a multi-line Python string containing embedded `"..."` to a
  native exe via `& $venvPython -c $harnessPy` mangles the inner double-quotes at the
  PowerShell->native argument boundary (error reports `File "<string>"`, not a path).
- Iter 3 (fix): write `$harnessPy` to a temp `.py` (UTF-8 no-BOM via
  `[IO.File]::WriteAllText` + `UTF8Encoding($false)`) inside a `try/finally`, then
  `& $venvPython $harnessTmp` -- passing only a path, no quotes to mangle. GREEN.

**Lesson (standing):** Never pass multi-line Python with embedded quotes/regex
through `python -c` from PowerShell -- the native-arg boundary strips inner `"`.
Neither expandable nor literal here-strings fix it. A probe that extracts the body to
a file and runs the file will NOT reproduce the bug (it bypasses `-c`); only a live
in-script run does. Fix: write a temp file and run the file. Lines 81/151 of the
script use `@"..."@` successfully because their Python has no embedded quote/regex
collisions -- left untouched (out of scope).

## 1. The OMIM 88-bug (root cause + fix)

### Symptom
`omim_n_diseases` was silently near-dead -- non-zero for only ~88 variants (0.00%) of the 4.4M cohort
across EVERY prior run. It escaped notice because the step-8 log printed "88" (a non-zero number, so no
existing zero-check flagged it).

### Root cause
`OMIMConnector._parse_mim2gene` read `mim2gene.txt`, whose own header states it is NOT a table of
gene-phenotype relationships. Its `PHENOTYPE_TYPES = {"phenotype","predominantly phenotypes"}` filter is
self-contradictory against that file: 'phenotype' rows carry ZERO HGNC gene symbols (0/8637), 'gene' rows
carry them (17682/17847) but were excluded by the filter; only ~36 oddball 'predominantly phenotypes'
rows happened to carry symbols -> the 88. `mim2gene.txt` contains no disease count at all.

The genemap2 autosomal-dominant fix from the prior arc was NOT the cause -- a baseline probe confirmed
mim2gene-alone ALSO produced 88, isolating the bug to the mim2gene source choice.

### Fix
Rewrote `OMIMConnector` to be genemap2-driven. `genemap2.txt` Phenotypes column (semicolon-separated
disease entries, each tagged with a mapping-key in parentheses) is now the sole source for all three
OMIM columns. New static helper `_count_phenotypes`; `_parse_genemap2` replaces
`_parse_genemap2_autosomal_dominant`; `_get_gene_table` is genemap2-primary with a relaxed mim2gene-None
guard so genemap2-alone works.

### Result (live re-probe, real 4.4M cohort + real genemap2.txt)
- `omim_n_diseases > 0`: 3,155,973 variants (71.74%) -- was 88. Bug dead. Graded 0-16, max matches genemap2.
- `omim_is_autosomal_dominant > 0`: 1,627,256 (36.99%) -- held ~37%, no regression.

## 2. New feature #88: omim_n_diseases_molecular

Added `omim_n_diseases_molecular` as feature #88 (87 -> 88): the count of disease entries with mapping-key
(3) (confirmed molecular basis). Wired through all four layers (connector, training builder in
real_data_prep, inference builder in variant_ensemble, API schema + row builder). Feature contract
updated: EXPECTED_TABULAR_FEATURE_COUNT 87 -> 88; INFERENCE_FEATURE_COLUMNS realigned; tripwire test green.

### Empirical surprise (recorded honestly): 0.9999 collinearity
I predicted `omim_n_diseases_molecular` would diverge meaningfully from `omim_n_diseases`. It does not.
Probe on the real cohort: the two columns differ for only 3,207 variants (0.07%); Pearson r = 0.9999;
the joint distribution sits almost entirely on the diagonal. Cause: the genemap2 (3) key dominates (86%
of 8,953 entries), and non-(3) entries concentrate in low-disease-count susceptibility genes, so per-gene
counts come out near-identical. The invariant molecular <= all holds (the 3,207 differing variants are real).
DECISION: keep the column -- it is correct, harmless, and semantically distinct (the (3) restriction is a
real definition even if currently collinear). Documented here so downstream feature-importance analysis is
not surprised by the redundancy.

## 3. Launch invocation audit: two more silent-zeros caught

An audit of how `launch_run17_baseline.sh` builds the `$ARGS` it passes to `run_phase2_eval.py` found:

1. `--omim-genemap2-path` was NEVER in `$ARGS`. The launch script predates the connector rewrite, so on a
   real run `omim_genemap2_path` would stay None and all three OMIM columns would silent-zero across 4.4M
   variants -- wasting the entire OMIM fix.
2. The script's hard-fail guard checked that `mim2gene.txt` exists (now inert) but did NOT check that
   `genemap2.txt` exists (now essential). The file the OMIM columns depend on had no preflight guard.

Both closed: a genemap2 file-pick + `--omim-genemap2-path` in `$ARGS` + a hard-fail guard (exit 8, loud
echo) mirroring the existing EVE/PhyloP/dbSNP/ClinGen guard pattern. `--omim-path` (mim2gene) kept for
backward-compat (the connector ignores it; harmless). Guard logic unit-tested: fires exit 8 when genemap2
absent, passes with correct ARGS when present. Placement verified: omim-path -> genemap2 -> PhyloP.

## 4. PhyloP pybigtools dependency gap

`pybigtools` (PhyloP's BigWig reader) was absent from BOTH `requirements.in` (the pip-compile source) and
`requirements.txt` (the file the VM installs from). The local proof used a venv where pybigtools was
hand-installed; the VM is a different machine, so PhyloP would hit ImportError -> silent phylop_score=0.0
on the real run despite the local success.

Fixed in three places:
- `requirements.in` under "# Annotation connectors": `pybigtools>=0.3.0`.
- `requirements.txt` hand-maintained tail (after transformers==4.46.3): `pybigtools>=0.3.0`.
- `launch_run17_baseline.sh` new step 4b: idempotent `pip install pybigtools>=0.3.0` + a hard
  `import pybigtools` verify (exit 4). Belt-and-suspenders, because launch activates a prebuilt /venv/main
  and does NOT pip-install from requirements at run time.

Pin is `>=0.3.0` (not ==): PyPI confirms 0.3.0 ships manylinux wheels for cp39/310/311/312/313, so any VM
Python gets a binary wheel (no Rust source build).
